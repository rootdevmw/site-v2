**Church of Christ at Red Cross — website design improvement plan**

Prepared 21 October 2026 from the current `site-v2` working tree.

The recommended direction is a warm, contemporary church website built around the congregation, a clear Sunday invitation, and practical ways to participate. Preserve the church's identity and approved teaching while improving the presentation, readability, and visitor journey. Extend the same identity into a clear, efficient administration interface and consistent account pages, with responsive behavior across all three areas.

This began as a source and asset review of the entire frontend. The route inventory contains 19 public page files, 58 dashboard page files, and four authentication page files: 81 page files in total, including the public root redirect and dynamic route templates. Route/component scans were followed by detailed inspection of the shared layouts, navigation, tables, pagination, forms, dialogs, editor, imports, representative management/detail pages, account flows, public pages, styles, relevant content types, congregation photographs, and logo assets. The initial review left application files unchanged. Authorized implementation is tracked below, preserving the user's existing working-tree changes.

Browser verification is excluded from this plan and its completion estimate. Validation uses source review, automated tests, TypeScript, targeted lint, production builds and relevant HTTP/API checks. Test results remain limited to the checks documented for each increment; fixture tests do not establish live HTTP/database, upload, email or concurrent-operation behavior. Responsive layout, keyboard access and accessibility requirements remain part of implementation.

**Responsive design rules and implementation coverage**

Adopt consistent mobile padding of approximately 16 px, increasing to 24–32 px as space permits. Let headers/actions stack, use `min-width: 0` where flex/grid children must shrink, wrap long user content, and keep page-level horizontal scrolling out of normal reading/form layouts. Allow a contained horizontal scroll region for data tables that truly need two-dimensional layout; do not hide overflow simply to mask a sizing problem. W3C's [reflow guidance](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) explains both the 320 CSS px baseline and the exceptions for genuinely two-dimensional content.

Make common phone actions comfortably tappable, aiming for roughly 44 px touch areas as a product design target. WCAG 2.2 AA's [minimum target-size criterion](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) uses 24 by 24 CSS px with exceptions; the 44 px design target should not be confused with that minimum. Provide a simple pointer alternative to program dragging, as described in [W3C's dragging guidance](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html).

**How to judge the result**

- At mobile and desktop widths, the first screen communicates the church's identity and offers Plan a visit and Watch online.
- Service times, service languages, the combined-service exception, and directions are easy to find and consistent across pages. Maintain one shared source of this information and display church-local times explicitly where needed.
- Public, account, and dashboard layouts follow the responsive implementation requirements, including 320 CSS px reflow, appropriate breakpoint boundaries, and support for zoom. Normal page content does not require horizontal scrolling; genuinely tabular regions can scroll within a labelled container without losing access to fields or actions.
- Dashboard navigation becomes a usable drawer on phones. Table/detail/form actions, notifications, CSV tools, dialogs, and editors remain reachable on small or short viewports and with a software keyboard.
- Portal view pages use the dedicated record-view designs rather than a generic list of labels/values. The Member, Event, and Prayer Request pilots establish the pattern; all remaining view families meet the same identity, hierarchy, action, related-data, and responsive criteria.
- Submitting a password or other form does not expand its button into a page-sized loading block. Empty, loading, failure, and success states remain visually distinct and stable.
- Navigation, forms, and media controls work by keyboard, have visible focus, and use appropriate accessible names and labels. Collapsed mobile navigation must not leave hidden links in the tab order. Use the [WCAG 2.2 guidance](https://www.w3.org/WAI/WCAG22/quickref/) as the accessibility baseline and aim for AA.
- The homepage does not eagerly load the ten full-resolution carousel originals. Establish an initial image budget of about 1 MB for the homepage and aim for a hero of roughly 150–350 KB, adjusting for visible quality.
- Target LCP at or below 2.5 seconds, INP at or below 200 ms, and CLS at or below 0.1 at the 75th percentile once field data exists, following [Core Web Vitals guidance](https://web.dev/articles/vitals).
- Handle unavailable content and API failures gracefully so a failed optional feed does not remove the essential welcome, service information, and contact details.
- Track visit-button clicks, direction clicks, stream/message starts, group inquiries, and form completion. Establish a baseline before setting improvement targets; keep personal prayer text out of analytics.

The first implementation milestone should combine the shared visual system with the P0 dashboard layout/table fixes, followed by the homepage and visit experience. This sequence improves both the congregation's public welcome and staff access to essential administration before the remaining page refinements.
